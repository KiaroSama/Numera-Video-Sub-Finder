### N28-01: complete saved-setup identity

The original `extract_dirty` compared region/range geometry and a tuple containing only language, device and quality. The production checkboxes for `gpu_required`, `normalize_persian` and `overwrite` changed the configuration directly. Toggling only one therefore left the Save dirty marker, native unsaved acknowledgement and source/project replacement guard falsely clean. The source-token baseline effect uses untracked configuration reads, so it did not compensate for the omission.

`crates/ui/src/project_save.rs::SetupSnapshot` now clones `ExtractConfig` and removes only `input`, `output` and `data_root`, which represent native grant/runtime locations. All 13 current durable fields remain significant, including regions, exclusions, time bounds, threads, confidence and accelerator requirements. Geometry undo remains a separate concern. A saved baseline comes from the actual saved candidate; edits made after the request retain their dirty state.

The new unit contract independently changes and restores each durable field and verifies that rebinding native locations alone does not mark a semantic setup dirty. The hosted GUI flow now toggles each of the three real checkbox bindings before later fixture edits, checks its boolean state and Save's accessible dirty marker, verifies unchanged source/ROI/range/transport state, then restores clean state. `setup-dirty-controls.json` explicitly identifies programmatic DOM input, not physical input or native picker qualification.

### N28-02: transactional Save and Save As

With a completed Review active, changing extraction settings can produce an empty setup candidate. Previously `persist_project` called native `replace_project`, installed that setup into the UI and reset selection/history before calling Save or Save As. A cancelled picker, declined replacement or write error thus left the in-memory Review replaced despite no accepted save. Existing staging already prevented accidental reuse of a completed Review's save path; the finding is not a claim that cancellation silently overwrote that completed file.

The repair uses the existing `save_project` and `save_project_as` commands with optional candidate project/source-token arguments. No new IPC command, permission or ACL is introduced. Legacy native/close calls can still save the active project without those arguments.

Native `project_save.rs` separates preparation from publication:

1. Under the operation lock, check admission and capture the original complete project identity, job, path generation and permitted active save path.
2. Validate the detached candidate using the existing native source grant, fingerprint and project validation. Preserve native Review source/model/config identity and restore only owned crop paths. Do not publish the candidate or change paths, recent history or dirty flags.
3. Release workspace locks for the picker and replacement confirmation. Cancellation returns without candidate publication. Preserve source-media destination rejection, absolute-path admission, prepared destination checks and explicit replacement consent.
4. Before writing, verify any native-close acknowledgement, reacquire the operation lock and reject changed jobs, generations, complete original project identity or newly dirty Review state. Do not roll back over a newer workspace.
5. Write through the existing atomic-output path. Only after success install the candidate, active path, bounded recent history and clean flags together.

UI `PendingSave` publishes an accepted setup only after `Ok(Some(destination))`. Cancellation/error preserves project contents, selected cue, undo/redo, revision, draft and dirty flags. Revision, Review generation, source token, draft and genuine close-state guards prevent late responses from replacing newer work. Later configuration changes remain dirty relative to the saved snapshot. After success, restore native unsaved flags from the actual current UI state; the notice distinguishes an earlier saved snapshot from the retained current workspace.

Independent review caught and corrected one candidate race before publication: a native save could commit, then a busy close acknowledgement could temporarily set UI `closing=true` before the successful save response arrived. Native rejects a busy close, so `Ui::close_snapshot` now reports that busy acknowledgement without entering UI close state. An admitted idle close still freezes publication. Both unlock/response orders and the genuine close guard have deterministic regression coverage.

Save controls and handlers now share admission for closing, ordinary busy work, preview decoding, active extraction and pending Review loading. Saving a dirty Review still retains its cues and undo/redo. Saving a setup from a completed Review still requires its own destination; later Save on that saved setup reuses the setup destination.

The native tests exercise picker cancellation, declined overwrite, controlled picker/confirmation/write failures, first setup save, successful saved-file readback, subsequent setup Save, stale generation/project/job/Review dirty state, invalid source/configuration, missing optional arguments, native Review path/metadata restoration, source-media protection and failed/successful close verification. Nine UI tests cover all durable fields, path rebinding, Review preservation, accepted setup/Review publication, newer settings, stale responses, busy-close order and Save admission. Together with the two catalog tests, this patch adds **21 Rust test functions**, with multiple independent cases inside several functions.

Durability boundary: an atomic-output directory-sync error can occur after destination bytes were published. Error handling preserves the old active workspace; it does not promise unchanged destination bytes after every possible late storage failure. The controlled write-failure regression fails before publication. This existing distinction must remain explicit in runtime acceptance.

### N28-03: Codex marketplace policy

The baseline catalog used `policy.authentication: "NONE"`. The official stable Codex `rust-v0.172.0` implementation at immutable [`3d86e43b075adeba2193ec5c22ac92f55afd82e6`](https://github.com/openai/codex/blob/3d86e43b075adeba2193ec5c22ac92f55afd82e6/codex-rs/core-plugins/src/marketplace.rs) accepts only `ON_INSTALL` and `ON_USE` for that enum. Typed deserialization occurs before per-entry filtering; the unsupported value rejects the manifest and its loader skips the catalog.

The catalog now uses the official default `ON_INSTALL`. The existing `xtask source-policy` validates the tracked catalog's local installation/authentication policies, including omitted/default fields and every entry. Null, wrong types, unsupported values and malformed containers fail with entry/field context. The tests exercise all supported combinations, the actual catalog and invalid values after a valid entry. This is a bounded policy validator, not a claim of complete schema or live installation testing across five hosts. No MCP server, credential or new dependency is introduced.

The current Claude `--marketplace` installation form was checked against its official CLI reference and retained. Do not replace current supported syntax merely because older instructions used another form.

### N28-04: responsive command header

The original Linux screenshots at `1280×860` and Windows screenshots at `1264×821` show the heading “Extract” wrapped letter by letter, with the rightmost command clipped. The action group was nonshrinking, the title could shrink/wrap anywhere, and hints/labels hid only below a narrower window breakpoint. A document-scroll-width assertion could pass because the workspace clips overflow.

The header is now a named inline-size query container. Shortcut hints collapse when its actual available content width is at most `1240px`, accounting for a wider sidebar as well as a narrower window. The title does not shrink or wrap. Existing icon labels, tooltips, keyboard shortcuts and the narrower icon-only breakpoint remain intact.

The existing layout group now records title line count, title bounds, all nine command rectangles and containment within both header and viewport. It checks widths `960`, `1280` and `1440`; the last uses the real sidebar separator's `End` handler and requires a rendered `260px` sidebar. It restores the separator/window on success or error. Input delivery is programmatic; no physical keyboard claim is made. The GUI denominator remains **28 groups**, and the proof descriptions now name the added assertions. No deadline, concurrency or timeout budget was raised.

## Finite follow-up and design decisions

The receiving reviewer should first use the owner's actual Rules, hooks and configured SpecKit chain. Private orchestration files are not public repository artifacts. Review the complete PR and the exact source, retain the regressions, obtain an approved hosted verification context, and require successful current-head reports and principal statuses before authorized integration. Do not confuse this audit author's PR-only permission with the owner's later merge/closure permission.

For the requested modern UI, Studio V2 already supplies persistent preview transport, Focus Mode, marquee zoom, stage resizing, notifications and language-pack discovery. Useful optional next choices are: clearer transport grouping with less always-visible shortcut text; a readable selected-region coordinate editor; and a compact extraction action area after checking ordinary production window heights. Evaluate each once against actual production dark/light layouts. A separate design preference is not evidence that the four finite defects above remain open. Do not import a React design system into this Leptos application solely to restyle controls, or assign `role="toolbar"` without implementing its keyboard model.

Dependabot already covers root Cargo, fuzz, Loom and GitHub Actions weekly. Evaluate unmaintained transitive dependencies through real compatible upstream upgrade/replacement paths; do not add blanket advisory ignores or unrelated dependency churn. Newly found reproducible defects belong in the same receiving session, with a counterexample, a repair and a bounded acceptance check. External approval or missing hardware must be recorded as a concrete blocker, never labelled DONE.

# Windows build and distribution

Builds run only in GitHub Actions: Windows 2025 x64 and Windows 11 ARM64 native hosted runners. Rust 1.99, pinned Tauri CLI, Clang/bindgen and Visual Studio SDK are prerequisites. Native FFmpeg/Tesseract are built from the pinned vcpkg baseline with dynamic release triplets; ONNX Runtime is the exact API31 CPU archive. The optional native visual helper explicitly selects the hosted ClangCL CMake toolset on both Windows architectures, with an ARMv8-A baseline on ARM64; MSVC's host-feature probing is not used for portable binaries. Native MSBuild node reuse is disabled so completed builds cannot leave reusable workers behind. Before provisioning, the installed Visual Studio Developer PowerShell entry point initializes the matching native host/target compiler and Windows SDK. CI exports only an allowlisted toolchain environment, preserves its project-owned temporary roots, and checks actual `errno.h`/`windows.h` admission plus the compiler's native PE architecture before Rust/bindgen runs. No SDK version or include directory is guessed. Before compiler setup, the ephemeral hosted runner sets and reopens Microsoft's version-independent `HKLM\SOFTWARE\Policies\Microsoft\VisualStudio\SQM` policy, requiring `OptIn` to be DWORD zero. The policy key is shared across registry views. CI also obtains `installationPath` and `installationVersion` from one component-qualified Visual Studio discovery record, derives the reviewed major's `VSCommon/<major>.0/SQM` opt-out, and verifies DWORD zero in both native and x86 registry views. No installation-folder or compiler-toolset version guess and no logical `Wow6432Node` prefix is used. The extra version-specific keys are supported by current first-party Visual Studio tooling, but a VS18 compiler non-spawn contract is not independently documented: the next actual compiler/tool builds must prove prevention. This opts out of optional diagnostic collection only, not required diagnostics or security checks. Actual `cb8db1b` Windows jobs still left owned `vctip` survivors despite these settings. For Rust stages, CI therefore selects one existing native LLVM tool directory, verifies the PE architecture of `clang-cl.exe`, `llvm-lib.exe` and `lld-link.exe`, and exports target-qualified C/C++/archive and Cargo linker paths. The selected MSVC ABI, SDK headers/libraries and release CRT remain unchanged; WASM does not inherit these compiler overrides. Missing/mismatched LLVM tools fail admission, with no silent fallback. At exact `0b63aea`, ARM64 passed native/Rust/tool stages without the earlier VCTIP rejection, while x64 llama CMake still selected `cl.exe` and left an actual owned telemetry child. Target-qualified Rust compiler settings do not select the separate CMake generator toolset; the explicit x64 ClangCL correction awaits hosted proof. This is a prevention candidate, not a verified fix: actual compiler completion and unchanged leak regressions must still pass; `vctip` is never ignored or killed by a name exception. The application never changes the user's registry. References: [Microsoft VSCEIP registry policy](https://learn.microsoft.com/en-us/visualstudio/ide/visual-studio-experience-improvement-program?view=vs-2026#registry-settings), [shared registry views](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys). No local build commands are part of the authorized workflow.

CI generates official ICO/PNG assets, builds GUI/CLI and assembles portable ZIP plus current-user NSIS. DLLs must be next to imported executables before main; the runtimes directory also supplies explicitly loaded libraries. Target architecture and closure are checked in provisioning/package inventories. The exact `XmlLite.dll` import is an OS-serviced component: CI requires it in the native Windows system directory with a compatible PE header, including the documented ARM64X system format on ARM64, and refuses to copy it into the runtime pack. Other unknown imports and debug/nonmatching CRT members still fail. Microsoft explicitly forbids redistributing this system DLL; see [Installing XmlLite](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee388577(v=vs.85)). Windows loader behavior on a hosted development runner does not prove minimum-OS clean-install behavior.

NSIS uses WebView2 download bootstrapper when a usable system WebView2 is missing; that installation step needs network. Ordinary extraction after resource provisioning remains local. Visual C++ redistribution rights and notices must be checked before public release. Unsigned compiler/packaging intermediates are not completed distributable builds. Final publication requires approved Authenticode identity and verified signatures; those signing inputs are currently unavailable, so publication is blocked. Installer/update/uninstall/data-retention and physical DirectML/CUDA execution remain unqualified; see validation status.
